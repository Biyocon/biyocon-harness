# Agent Note: 在停止提示前完成 Cordis 激活

Status: implemented

[English](2026-10-29-cordis-tool-round-wake-order.md) | 中文

## 问题

Cordis 激活会异步投递通知，即使没有新的用户消息，也可能开启一个轮次。如果浏览器场景在初始轮次结束后就提交停止请求，而激活尚未完成，那么每条已录制响应由哪个轮次消费就取决于调度顺序。等待下一个轮次结束并不能确定完成的是哪条消息。只检查当前可见的最近一次完成可能漏掉排队中随后失败的轮次，而包含该失败的 golden 又可能接受它。

## 决策

[Cordis 浏览器场景](../../../../apps/web/tests/cordis-tool-round.e2e.ts)明确排列三个完整轮次：审批仍在等待时先结束初始请求；测试批准激活并等待通知轮次完成；最后才提交停止请求。提示要求对该通知只回复文本 `CORDIS_UI_ACTIVE`。这条回复之后浏览器标记仍然存在，实际停止调用完成后才消失。

`assertCompleteCordisLifecycle` 要求恰好三个 `turn/end` 事件，且它们的 `reason` 全部为 `completed`，同时要求四个预期的 Cordis 调用均成功。record 模式的驱动在提取 fixture 前执行该断言。replay 在比较对话 golden 前执行它，因此失败轮次不能成为可接受的 UI 基线。

会话 fixture 和 UI golden 来自通过[真实 Web 重放车道](2026-07-24-web-gui-browser-e2e-lane.md)成功执行的场景。现有录制清理器与规范化规则保持不变。共享的 `whenTurnSettled` API 仍表示等待下一个轮次；场景负责在注册每个等待之前确定允许执行的工作。

## 曾考虑的替代方案

**延迟 STOP 或重试失败的重放。** 延迟无法确定完成的是哪项工作，重试则可能选中有利的顺序。两者都不能证明整个对话已完整结束。

**把激活通知扣留到 STOP 到达。** 这适合作为反向调度实验，但把该 fixture 纳入正式测试会为了保留顺序不明确的录制而改变通知投递。它也无法覆盖停止请求之前独立完成的激活轮次。

**刷新包含失败的 UI，或只检查最近一次完成。** 这些做法可能把错误保留为预期输出，或在排队工作失败前就检查完成状态。会话记录与每一个轮次结束状态都必须表明成功。

## 后果

录制在请求和停止回复之外，还包含一次明确的激活确认。录制时因此多消耗一条模型响应，但对话的因果顺序可以直接审阅。产品代码、审批行为、超时、重试策略与 normalizer 均不变。

## 验证

该浏览器文件检查真实审批、已挂载的浏览器标记、所有轮次结束、成功的工具结果以及对话 golden。连续无密钥重放验证成功顺序。临时反向控制把真实激活通知扣留到 STOP 被接收之后；三轮次断言用明确的诊断拒绝这一顺序。该控制仅作为调查证据，不进入提交的运行时或测试组合。
