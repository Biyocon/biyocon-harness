# Agent Note: Devil's Advocate challenges analysis reports

Status: implemented

English | [中文](2026-10-28-conductor-analysis-critic.zh.md)

## Problem

Analysis could accept a producer's report after Auditor and Arbiter without an independent challenge to its reasoning. Auditor checks factual claims and file/line references; that does not establish that priorities, alternatives, risk trade-offs or recommendations follow from the cited material. The owner reports that CON-2026-0687 (CustomAgents) and CON-2026-7660 (biyocon-harness) both reached Arbiter acceptance without a Devil's Advocate critic. Reported role tokens were Detective 303K/378K, Strategist 150K/138K, Auditor 165K/196K and Arbiter 30K/26K, respectively. These are owner-reported observations, not replayed sessions; no private session content is included.

On [biyocon/master 45d316f](https://github.com/Biyocon/biyocon-harness/tree/45d316f852a7ad104375e07a148a48ca67f3b730), [admittedRoute and reportProducer](https://github.com/Biyocon/biyocon-harness/blob/45d316f852a7ad104375e07a148a48ca67f3b730/packages/conductor/conductor/src/intake.ts#L159-L179) routed Detective-entry recommendations through Detective → Strategist → Auditor → Arbiter, and an answer through its entry role → Auditor → Arbiter. Devil's Advocate could produce an entry-C report but did not challenge another report. [driveAnalysis](https://github.com/Biyocon/biyocon-harness/blob/45d316f852a7ad104375e07a148a48ca67f3b730/packages/conductor/conductor/src/analysis.ts#L153) drove those read-only stages. [recordGate](https://github.com/Biyocon/biyocon-harness/blob/45d316f852a7ad104375e07a148a48ca67f3b730/packages/conductor/conductor/src/state.ts#L235) requires an approved execution baseline only for implementation-C pass; [parseAnalysisState](https://github.com/Biyocon/biyocon-harness/blob/45d316f852a7ad104375e07a148a48ca67f3b730/packages/conductor/conductor/src/analysis-persistence.ts#L14) rejects analysis execution authority. The record format at that baseline was [v4](https://github.com/Biyocon/biyocon-harness/blob/45d316f852a7ad104375e07a148a48ca67f3b730/packages/conductor/conductor/src/state.ts#L35). The implemented [intake and report-completion note](2026-10-25-conductor-intake-and-report-completion.md) owns admission; this decision owns the added critique.

## Decision

Every analysis run requires a Devil's Advocate challenge, with no silent opt-out. The seven role identities and all required intake/preparation steps remain. The six admitted combinations have these paths; Gate C records separate `producer` and `critic` occurrences when Devil's Advocate is the entry role. Gate D (Headsman) and Gate F (Integrator) are always skipped in analysis.

| Entry | Deliverable | Producer and required preparation | Critic | Fact check | Decision | Skipped gates |
| --- | --- | --- | --- | --- | --- | --- |
| Detective | recommendations | Detective (A) prepares scope; Strategist (B) produces | Devil's Advocate (C) | Auditor (E) | Arbiter (G) | D, F |
| Detective | answer | Detective (A) | Devil's Advocate (C) | Auditor (E) | Arbiter (G) | B, D, F |
| Strategist | recommendations | Strategist (B) | Devil's Advocate (C) | Auditor (E) | Arbiter (G) | A, D, F |
| Strategist | answer | Strategist (B) | Devil's Advocate (C) | Auditor (E) | Arbiter (G) | A, D, F |
| Devil's Advocate | recommendations | Devil's Advocate (C, producer) | Devil's Advocate (C, critic) | Auditor (E) | Arbiter (G) | A, B, D, F |
| Devil's Advocate | answer | Devil's Advocate (C, producer) | Devil's Advocate (C, critic) | Auditor (E) | Arbiter (G) | A, B, D, F |

Both entry-C deliverables use two fresh, distinct Devil's Advocate children. Typed dispatch mode (`producer` or `critic`), distinct child IDs, attempts, prompts, source sessions and stored outputs distinguish them; the critic receives the candidate and referenced material, not the producer's prior transcript. This is separation of work and context, not an assertion that the same role has an independent viewpoint. Arbiter checks that provenance and cannot accept a candidate reviewed only by its own producer child.

The critic precedes Auditor. It asks whether priorities, alternatives, omitted risks, assumptions and recommendations follow from the evidence; it does not recheck every file/line citation. Auditor then verifies facts and exact citations in the final candidate, including any factual premise promoted from the challenge. Every new candidate version, whether caused by Gate C, Auditor or Arbiter rework, requires a new challenge before a fresh audit; Arbiter accepts only the latest exact candidate, matching challenge and matching audit. A citation defect in the candidate uses Auditor's existing Gate E `defect: analysis` rework to the producer, then the new candidate passes through critic and Auditor again. A defect confined to Auditor's own report uses Gate E `defect: report` to retry Auditor against the unchanged candidate and valid challenge. Gate E counts both Auditor rework paths; Gate C counts critic rework. This keeps critique and factual verification distinct and prevents auditing a candidate that critique will immediately replace.

### Challenge result and Gate C

The dedicated `AnalysisChallenge` structured result contains `run_id`, `purpose: analysis`, `candidate_hash`, `candidate_version`, ordered `material_ids`, `critic_child_id`, `critic_attempt`, `findings` with stable ID, severity (`minor`/`major`/`critical`), claim, rationale and material IDs, `conclusion: holds|does_not_hold`, a validated `defect: scope|plan|report`, and a bounded summary. `defect` is required for `does_not_hold` and forbidden for `holds`. The runtime computes a challenge hash from validated content. The result has no execution baseline, implementation approval or command evidence. A Gate C history record binds mode `critic`, child/attempt, candidate hash, challenge hash and decision. The existing entry-C producer pass is explicitly mode `producer`; neither can impersonate the other. A `holds` result with unresolved major/critical findings is contradictory and rejected.

Validation rejects a foreign run, unknown material ID, stale candidate/version/hash, reused child or attempt, mismatched dispatch mode, duplicate/conflicting challenge, changed finding content under the same hash, out-of-order Gate C and an Arbiter decision without matching candidate/challenge/audit hashes. Missing or forbidden `defect`, a Detective-producer `plan` defect, or a defect whose target violates the admitted route or typed producer/critic order makes the result malformed. A malformed result is a report-validation failure at the critic, never a synthetic `holds`. The runtime persists the exact candidate → challenge → audit → Arbiter links before dispatching successors; replay validates the same causal sequence and rejects a partially checkpointed or contradictory record. A crash before the challenge checkpoint cannot turn an unrecorded result into a pass; restart resumes only the durable stage or parks ambiguous dispatch for owner review.

`CONDUCTOR_RECORD_FORMAT_VERSION = 5` gives the durable run its complete analysis-critique meaning. Every run has a required `analysisChallenges: CapturedAnalysisChallenge[]` (empty for implementation); each entry stores the validated result, its runtime hash, candidate hash, critic child ID and attempt. Each v5 analysis candidate also stores typed `material_spans` (`material_id`, inclusive `start_line`/`end_line`) for its cited captured materials; the host validates the spans against the admitted material hashes before constructing critic input. Analysis Gate C history distinguishes `mode: producer|critic`; successful producer records bind their candidate hash, while critic records bind that candidate, challenge hash and child/attempt. Analysis `ReportDecision` requires `challenge_hash` alongside its candidate/audit hashes. These v5 fields make producer and critic occurrences, replay order and Arbiter acceptance unambiguous. v4 has no challenge provenance and is rejected with the existing unsupported-format error, without migration or compatibility shim. Implementation-only v5 records keep their current authority rules. [#30 phase 2](https://github.com/Biyocon/biyocon-harness/issues/30) must take the next monotonic format version (v6 if it follows v5 directly), never reuse v5 with a different meaning.

### Rework, owner and authority

A validated `does_not_hold` records critic Gate C rework. Its typed `defect` alone determines the target: `scope` → Detective, `plan` → Strategist, `report` → `reportProducer(admission)`. `plan` is invalid when the producer is Detective; the runtime rejects any target disallowed by the existing prerequisite route and never infers the defect or target from free text. The selected path uses the existing prerequisite rules and typed mode order, including an entry-C producer and critic at the same gate; a new candidate version/hash then requires a new critic child and audit. A valid critic `report` rework to the producer is distinct from a malformed critic report retried at the critic stage; the runtime represents these as separate typed transitions. A malformed critic result is the critic's report failure: the driver records Gate C `defect: report` and dispatches a fresh critic child/attempt against the same candidate without rerunning the producer. It consumes one `maxReworkPerGate` Gate C rework, not Gate E or an owner reassessment. The same per-run Gate C budget also counts substantive critic rework and, for entry C, producer rework; it is not reset by a new candidate. With the current configurable default of two reworks, the third Gate C rework request escalates with unresolved findings instead of another child dispatch. Gate A/B/E/G counters remain independent. A foreign/stale identity or authority violation fails closed and escalates immediately. Critical safety or authority findings escalate immediately with the exact reason; a substantive but repairable major finding uses rework. No verdict silently passes a challenge.

When a validated substantive challenge exhausts Gate C automatic rework, its gate record retains the typed defect and target while the run parks for an owner question. `answer_continue` consumes the exact owner plan and resumes that validated target, producing a new candidate and fresh critic before Auditor without resetting the Gate C budget. If a critic child starts and then fails, the runtime checkpoints a terminal Gate C authority block with its child ID, run-wide attempt and known token usage; it neither treats the failure as a malformed challenge nor offers owner-directed repair. A failed start before child creation records no child or attempt.

The runtime reuses [#37's owner ledger and continuation](2026-10-30-conductor-owner-escalation-resumption.md): exact run, candidate/challenge hash, gate history index, exact child attempt, and required questions are stored in the existing question/answer/consumed/rejected ledger. `maxOwnerReassessmentsPerGate` remains independently bounded. It emits the required `conductor/owner-question-created`, `conductor/owner-response-recorded`, `conductor/owner-response-acknowledged`, `conductor/owner-continuation-consumed` and `conductor/owner-terminal-rejection` events and uses the existing owner card actions `approve`, `reject`, `answer_continue` (Godkend / Afvis / Svar og fortsæt). `approve` is offered only for a concrete validated proposal; an analysis answer or approved clarification may trigger one read-only reassessment, never execution approval. An owner reply cannot create an execution baseline, authorize implementation, reset Gate C rework, or reach Headsman, Ralph, Integrator or closeout. Implementing recommendations needs a separate implementation run and its own authorization.

### Input, cost and presentation

The critic receives the latest candidate report, its content hash/version, acceptance criteria, the bounded material-reference index and deterministic excerpts. The candidate's typed material spans identify captured material IDs and inclusive line ranges. The runtime, not a model, validates each span against the immutable admission capture and its hash, selects those exact lines, enforces `maxCriticInputTokensPerAttempt`, and logs the exact excerpts and complete model-visible request in the child session before dispatch. Missing, out-of-range or over-budget spans block the critic dispatch instead of silently truncating evidence. Detective's repository exploration and full child transcript are not replayed. Intake rejects image attachments before analysis admission; image analysis needs a separate issue and design. The critic has only `structured_output`; no `read`, `read_image`, `grep`, `glob`, write, edit, shell or other file tool. [ToolRestriction](../../../../packages/conductor/tool-conductor/src/capability.ts) filters tool names only, so it cannot enforce path access from material IDs; runtime-owned excerpts avoid that gap. The challenge result and Gate C state are checkpointed, and the logged request plus captured material hashes allow reconstruction of everything the critic saw.

The canonical [Devil's Advocate role instructions](../../../conductor/roles/03-devils-advocate.md) and [conductor-specialist skill](../../../skills/conductor-specialist/SKILL.md) define a typed analysis `critic` mode alongside the existing `producer` mode. In critic mode the role returns `AnalysisChallenge`: a candidate-bound conclusion, falsifiable reasoning findings, alternatives, omitted risks and material IDs; it does not produce a replacement candidate or audit citations. Both canonical files declare the supported analysis modes in parsed metadata; preset validation checks for `critic` there rather than inferring it from prose. [Source launch](../../../../apps/cli/scripts/source-launch.ts) regenerates the installation skills at each startup under #25/#59. [Preset validation](../../../../packages/conductor/conductor-presets/src/index.ts) rejects a role or specialist skill lacking the critic mode, even if the asset exists, so a stale producer-only instruction cannot mount.

The model-hidden `conductor/child` event carries role, attempt and gate; typed dispatch/stage data adds producer/critic mode and exact child binding for EN/DA presentation. [#56](https://github.com/Biyocon/biyocon-harness/issues/56) owns browser-tab and breadcrumb names. A fresh child starts with no inherited gate badge, and UI text names `holds`/`does_not_hold` or pending/escalated without relying on color.

The owner's two reported runs used 648K and 738K tokens across the four listed roles. The estimate is 20–40K additional tokens for one bounded critic attempt, about 3–6% of those totals; two reworks can mean three attempts (60–120K additional critic tokens), excluding producer reruns. The validated `tool-conductor` Config fields, overridable in `cordis.yml`, are `maxCriticInputTokensPerAttempt` (default 24,000), `maxCriticOutputTokensPerAttempt` (default 16,000, including reported reasoning output) and `maxCriticTokensPerRun` (default 120,000, counting all provider-reported input, output and reasoning tokens without double counting). The loader validates positive safe integers and a run ceiling at least as large as the sum of the configured per-attempt input and output caps and rejects invalid preset config at load. The host reserves that sum before dispatch, requires the provider output cap to include reasoning tokens, records actual usage per attempt, blocks missing or excessive usage, and ends the run with the consumed, reserved and limit token counts if the remaining run budget cannot admit another attempt. The three limits are recorded in the admitted run and do not change when deployment Config changes. Missing usage charges the full reserved allowance. A provider unable to enforce the cap is rejected. No limit is hardcoded in dispatch logic. Critique is mandatory for every analysis run. A future opt-out, if ever introduced, must be explicit and logged per run, never a hidden configuration switch. [#58](https://github.com/Biyocon/biyocon-harness/issues/58) owns Detective cost reduction; this decision neither expands Detective input nor authorizes a second whole-repository exploration.

## Alternatives considered

**Critic after Auditor.** It repeats citation checking or invalidates an expensive audit when it demands a new candidate; challenge before audit is cheaper and keeps responsibilities distinct.

**Auditor as sole critic.** Auditor already owns factual and citation verification, so combining reasoning challenge with that pass hides which judgment failed and would leave the reasoning gap.

**Optional or silent critique.** It allows an accepted analysis to bypass the owner's requested role and makes restart semantics dependent on an unrecorded choice. Mandatory critique has a visible token cost and a stable route.

**Treat a second Devil's Advocate child as fully independent at entry C.** A fresh session and separate mode prevent self-review of one child output, but the same role/model is not an independent discipline; provenance must state that limit.

## Consequences

The added critic increases latency and tokens, especially after rework; the bounded input, usage ceiling and explicit owner stop prevent silent cost growth but do not reduce Detective's existing cost. Entry-C producer/critic children share a role/model, so the runtime guarantees separate sessions and evidence binding, not independent expertise. v4 runs cannot resume under v5; pre-release rejection is intentional. The route changes neither #30 phase-1 behavior nor implementation authorization.
