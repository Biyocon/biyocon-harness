# Agent Note: 公共 fork CI 运行器配置

Status: implemented

[English](2026-10-18-public-fork-ci-runner-profile.md) | 中文

## 问题

主要 CI 工作流使用组织管理的大型运行器标签，并通过仓库变量向持久化自托管池提供故障切换。由个人账户拥有的公共 fork 无法分配这些组织运行器，因此在没有 fork 专用运行器配置时，四个受影响的作业会一直排队。复用自托管故障切换并不安全，因为公共仓库的拉取请求可以执行贡献者控制的工作流代码，而持久化运行器会在作业之间保留凭据、网络访问和主机状态。

## 决策

只有当拉取请求头仓库存在、其仓库 ID 和所有者 ID 与当前仓库上下文匹配，并且 `fork` 字段是布尔值 `false` 时，三个 Linux Node 24 作业、`all checks passed` 判定作业和原生 Windows 作业才会使用已配置、企业或自托管路由。任何缺失、null、空、类型不同或不匹配的值都不受信任，并使用带公共并发配置的 `ubuntu-24.04` 或 `windows-2025`。仓库本身是 fork 时，即使拉取请求来自同一仓库，也仍使用安全的托管路径。这个正向信任判断先于 `DSH_CI_FAILOVER_LINUX` 和 `DSH_CI_FAILOVER_WINDOWS`，因此仓库变量无法把不受信任的工作路由到持久化运行器；明确受信任的头仓库保留 Dependabot 例外和变量控制的故障切换行为。

公共 fork 配置将 Linux 静态门禁限制为两个并发门禁，将覆盖率限制为两个测试工作进程和一个门禁，将消费端门禁与代码检查器限制为两个工作进程，并将快照限制为四个工作进程。原生 Windows 使用一个覆盖率工作进程、一个门禁工作进程和两个 publint 工作进程。这些值适配标准托管运行器的四个 CPU，同时不改变非 fork 仓库所用的大型运行器或自托管限制。

即使存在故障切换变量，不受信任或未知的拉取请求元数据也默认使用托管缓存恢复和 Playwright 依赖安装。只有同一个正向仓库、所有者和布尔非 fork 判断才能选择自托管 Playwright 步骤。非拉取请求的自托管热备演练和组织运行器基准作业保留顶层 `github.event.repository.fork == false` 守卫，因为相应的推送和 `workflow_dispatch` 事件没有拉取请求头仓库。

Linux 配置从 Ubuntu 安全归档下载 Bubblewrap `0.9.0-1ubuntu0.3`，遇到传输或 HTTP 失败时转向 Linux Kernel Archives 提供的 Ubuntu 镜像。两个端点使用不同的 DNS 域名 `ubuntu.com` 和 `kernel.org`，因此一个域名解析失败时，恢复不必再依赖同一个 DNS 域名。两个位置都必须在解包前提供 SHA-256 为 `2461f1beee9cb04c8942739fe1a2b37e7b7c2a3d518f0779dc75f9245baa3094` 的制品。每个镜像最多传输两次，连接超时为五秒，单次传输超时为十五秒，配置的重试间隔为一秒，重试窗口为二十秒。在窗口内开始的传输可以在窗口结束后完成，因此两个镜像合计的时间额度约为 70 秒。校验和不匹配会立即终止，而不会尝试另一个镜像。两个镜像均失败也会在修改可执行文件路径、AppArmor 设置或运行 Bubblewrap 探测之前终止准备。

## 曾考虑的替代方案

**在公共 fork 中注册永久自托管运行器。** 否决，因为贡献者控制的拉取请求可能在持久化机器上执行。允许 fork 和外部贡献后，仓库成员身份不再是充分的信任控制。

**从个人 fork 使用组织管理的大型运行器。** 否决，因为这些标签属于上游组织，而且个人账户仓库无法使用大型运行器。

**为所有仓库替换企业拓扑。** 否决，因为现有的非 fork 池与故障切换开关仍然有用，并且已有独立的就绪检查。fork 条件可以隔离公共 fork 策略，而不削弱或复制这些行为。

**依赖单个不可变的 Launchpad Librarian 对象或 ubuntu.com 下的两个主机。** 否决，因为制品身份并不能保证网络可用性，而且两个 Ubuntu 托管名称可能在同一次 CI 运行中都无法完成 DNS 解析。独立运营的归档镜像提供同一份固定字节，而有界重试避免小型依赖下载阻塞 CI 多分钟。未经验证的镜像或未固定版本的软件包管理器安装都不能替代必需的校验和。

## 后果

不受信任的拉取请求头可以在临时 GitHub 托管机器上运行主要的无密钥 CI，但四个受影响的作业拥有更少的 CPU，运行时间可能更长。需要密钥的真实 API E2E 对 fork 和 Dependabot 拉取请求仍保持跳过。fork 仓库不会运行自托管热备演练或组织运行器基准作业。工作流测试会锁定正向仓库、所有者和非 fork 信任判断、安全托管默认值、并发、设置以及非拉取请求保护条件，使后续故障切换修改无法悄然恢复未知或不受信任的头仓库到持久化运行器的路由。

Ubuntu 归档可能移除已被替代的软件包版本。如果两个固定位置均消失，CI 会明确失败，直到维护者审查替代版本及其校验和；绝不会静默安装最新软件包。准备成功仍然要求真实的 Bubblewrap 隔离探测通过。

## 验证

`scripts/ci-workflow.spec.ts` 解析组装后的工作流，并验证每个公共 fork 运行器选择都先于故障切换变量、保守的工作进程限制存在、托管 Playwright 设置保持启用，以及持久化主机和企业基准作业都要求非 fork 仓库。`scripts/prepare-ci-bubblewrap.spec.ts` 使用隔离的命令夹具调用真实准备脚本，并在不访问网络的情况下验证固定制品、有界 curl 参数、镜像故障切换时替换不完整下载、任一镜像的校验和失败均立即拒绝、镜像耗尽时拒绝，以及操作顺序。仓库验证还会运行类型检查、代码检查、文档同步、变更范围和空白检查。
