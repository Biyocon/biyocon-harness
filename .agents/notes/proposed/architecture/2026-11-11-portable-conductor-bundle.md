# Agent Note: Portable Conductor bundle

Status: proposed

English | [中文](2026-11-11-portable-conductor-bundle.zh.md)

## Problem

The Conductor run engine is divided into reusable packages, but the installed product is not an independent plugin. The CLI owns the `conductor` preset and copies its role and protocol files from the repository before launch. An `npm pack --dry-run --json --ignore-scripts` check found eight files and no role or protocol assets in `dsh-conductor-presets`, while the CLI tarball contains 29 Conductor preset files. The base and Web bundles mount Conductor unconditionally, while generic question UI and host APIs contain Conductor-specific owner interactions. Installing the current `dsh-conductor-presets` package into another DeepSeek Harness fork therefore does not install the preset, its instructions, or all required host behavior. The owner needs one Conductor runtime that Biyocon Harness and a separate Harness fork can install; client adapters and public release follow separate designs and decisions.

## Proposal

Make one versioned Conductor engine distribution whose canonical runtime remains in `packages/conductor/*`. Thin host bundles compose that same engine and its packed role, protocol, template, and image assets for each supported Harness host line. A separate optional Web UI bundle owns Conductor-specific subagent and owner-question presentation. Biyocon and another Harness fork install the same engine packages without copying source; each selects its compatible host bundle. The generic base, Web bundle, preset picker, session reader, and question UI gain only small reusable plugin extension points where required. The core never imports Conductor. The [core dependency inventory](2026-11-05-conductor-core-dependencies.md) records each host change with its file, purpose, and PR.

The first rc.7 extraction slice is a packed host bundle and preset, with no client adapter or record change. [`composeProfile`](../../../../apps/cli/src/profile-boot.ts) currently replaces `agent-presets.roots` with the CLI's shipped directory after bundle composition, so a bundle patch cannot register its own preset. Add an optional `dsh.bundle.presetRoot` relative to each installed bundle. Resolve the root by realpath and reject escapes from the installed package, including symlink escapes. Only a bundle explicitly named in the profile receives system trust; transitive dependencies do not. Reject duplicate ids across every system root, including the CLI's own directory, rather than shadowing them. Test all three rules. Move Conductor out of the CLI's shipped root and base bundle into the new bundle in the same change, then list it explicitly in Biyocon's profiles.

The package asset allowlist contains `.agents/conductor/README.md` and `roles/profiles.yml`; `00-conductor.webp` only for the Conductor role; role stems `01-detective`, `02-strategist`, `03-devils-advocate`, `04-headsman`, `05-auditor`, `06-integrator`, and `07-the-arbiter`, each with exactly `.md` and `.webp`; templates `baseline.md`, `closeout.md`, `dispatch.md`, `gate-decision.md`, `run.md`, and `specialist-envelope.md`; and `SKILL.md` from exactly `conductor-closeout`, `conductor-orchestration`, `conductor-ralph`, and `conductor-specialist`. These 27 asset files plus `preset.yml` and `agent.cordis.yml` match the current 29 CLI preset files. The manifest maps those literal source paths to package resource paths and hashes; adding another file requires an explicit manifest change. The package build uses that manifest, and `npm pack` verification compares the complete resource subtree and hashes against it.

### Event replay and existing sessions

Choose the required-bundle rule: a host profile opening a session with Conductor history must enable the Conductor host bundle. Its seven required events are `conductor/checkpoint`, `conductor/child`, and five owner-interaction events; [the owner-event tests](../../../../packages/conductor/conductor/tests/owner-events.spec.ts) assert that none carries `ignorable: true`. Before any session open, cold replay, or projection, the host composes the selected host profile's explicit bundles and registers their validated event declarations. The reader rejects a Conductor-bearing session when that bundle is absent, naming the required event and asking for a compatible bundle; it must not silently show a partial chat or interpret the run. The generic host remains usable for sessions without Conductor events, and no fixed Conductor name list or Conductor import enters core.

Existing Biyocon sessions are not rewritten. Biyocon host profiles continue to name the bundle, so their Conductor history and full chat remain readable. Records in unsupported Conductor run formats still display as unavailable through [the existing run-availability behavior](../../implemented/bug-fix/2026-11-06-conductor-unsupported-record-history.md) while the bundle is enabled; their run operations remain strictly refused. Opening those sessions in a host profile without the bundle instead fails before replay. Implement and test this event-registration mechanism before either clean-fork stopgate.

At upstream master [`e8f7b93a`](https://github.com/deepseek-ai/deepseek-harness/tree/e8f7b93a344964de3dca1ace9e72b6e4d6de87cb) on 11 November 2026, [declarative preset rows](https://github.com/deepseek-ai/deepseek-harness/blob/e8f7b93a344964de3dca1ace9e72b6e4d6de87cb/packages/preset/agent-preset/README.md) replace directory presets, and [`dsh.bundle.patch`](https://github.com/deepseek-ai/deepseek-harness/blob/e8f7b93a344964de3dca1ace9e72b6e4d6de87cb/packages/bundle/web-app/package.json) accepts ordered files. `presetRoot` is an rc.7 host seam, not an upstream installation mechanism. A thin upstream bundle must declare the same engine through that host's preset row; its service and record compatibility remain unproven. Pin each host line and verify its packed installation separately. Do not claim that one identical host bundle works on both.

The three Conductor packages (`conductor`, `conductor-presets`, `tool-conductor`) currently use `@deepseek-ai/*` names, and the tool peers on the other two. Local tarball installation tests may keep those names while proving a complete version-locked dependency closure without workspace links. Publisher-owned names for the entire distribution, license/provenance checks, and an owner decision belong to the later public-release stage; current names do not authorize publication under `@deepseek-ai/*`. Adopting names outside `@deepseek-ai/dsh-*` requires revising the package-naming rule in [AGENTS.md](../../../../AGENTS.md) in the same public-release decision; until then, packages retain their current names. Preserve peer identity for Cordis and shared Harness services so installation does not load a second core. The upstream [plugin installation guide](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/publish.md) describes `dsh plugin --profile <name> add <package>` and bundle composition; test its actual command against the selected host version and packed dependency closure. Biyocon Harness remains on rc.7; each newer upstream host requires an explicit compatibility check.

### Host security and lifecycle

One Harness host owns each run and its session log. No concurrent clients operate until a revised [#87](https://github.com/Biyocon/biyocon-harness/pull/87) design is approved and merged, and its host-level home/session-store lock is implemented and verified; #87 is not currently approved. Adapters must not launch independent writers for the same `DSH_HOME`. A client disconnect does not finish, cancel, or duplicate a run. Version 1 adapters use typed run/session identities for start, status, result, and resume only. Owner answers and Gate C approvals remain in the host's own UI; an adapter cannot submit either. Read-only analysis grants no write or release authority. No adapter exposes arbitrary files, credentials, or private role definitions.

The [installed-skill decision](../../implemented/bug-fix/2026-10-24-conductor-installed-skills.md) still governs trusted host reads, isolated skill precedence, and failure before publication. The [runtime decision](../../implemented/feature/2026-09-11-conductor-runtime-layer.md) still governs gates and tool enforcement. This proposal changes packaging and host composition, not those decisions. The shared v6 design for #75 phase 2, #30 phase 2, and #58 phase B needs its own review before any record or runtime-format change; packaging may be verified against the current format without claiming the final runtime is complete.

### Later client adapters

After both clean-install stopgates and the optional UI bundle, write a separate adapter design for ChatGPT Desktop, PI-Desktop, Super-Desktop, and Multica. Its first version may expose only start, status, result, and resume through one host API and a narrow MCP facade; resume refuses a pending owner question, while owner answers and approvals stay in the host UI. Each client's normal-UI acceptance and connection permissions belong to that later design, not to this packaging acceptance.

## Alternatives considered

**A separate Conductor service as the primary product.** It could serve MCP clients directly, but it would not make Conductor installable as a DSH plugin in another fork. It would also add a second host lifecycle and session-store owner. Keep a service or MCP facade as an optional adapter in front of the packaged DSH runtime.

**Copy the CLI preset and source assets into every fork.** It permits a quick local trial but duplicates authored roles, package wiring, and updates. It cannot establish that the packed plugin is self-contained.

**Move all Conductor-specific host behavior into generic core.** This would make the host depend on Conductor and burden installations without it. Generic registration points with optional Conductor providers preserve the dependency direction.

**Keep a fixed Conductor event-name list in core.** It would let a host without the bundle parse the seven required types but falsely suggest that their owner and run meaning is available. It also makes core track optional plugin names. Require the bundle for Conductor-bearing sessions instead.

**Mark future Conductor events ignorable.** Skipping an unknown run or owner event can lose authorization or replay facts while leaving a plausible partial session. The existing seven events are required and cannot be retroactively made ignorable without rewriting stored logs. Keep required-event refusal.

## Acceptance criteria

Deliver in this order: rc.7 host bundle and preset from the explicit asset allowlist; the pre-read event-registration mechanism; stopgate 4a; pinned-upstream compatibility and stopgate 4b; optional Web UI bundle; then a separately reviewed adapter design and implementation. Do not merge an intermediate extraction that prevents existing Biyocon sessions from opening. The new host bundle registers both Conductor projections. Its package build and pack gate prove the required files and source hashes, reject extra/private files, and no CLI-generated copy remains. Preset-root tests prove realpath containment, explicit-profile trust, and duplicate-id rejection across all system roots. Event tests prove that all seven types load with the bundle, that a Conductor-bearing session without it is refused before replay, and that ordinary chat sessions still open without it.

Stopgate 4a is a keyless clean rc.7 installation using only packed artifacts, the documented profile command, and synthetic session records: package/dependency identity, composition, analysis/gate replay, existing format-5 and unsupported-format run visibility with the bundle, missing-bundle refusal, reload, and host restart. No Biyocon checkout, source-tree copy, private data, or manual preset transfer is present. Stopgate 4b repeats the relevant keyless installation, replay, and absent-bundle checks against one pinned newer upstream Harness version, proving its host services and record handling rather than assuming compatibility from package installation. Biyocon and the other fork must use identical canonical engine packages with their respective thin host bundles. Paid model calls require separate owner approval and are not part of either stopgate. The optional UI bundle and client adapters follow; public release later requires owned package names, license/provenance and secret audits, installation docs, a host compatibility matrix, and a separate owner release decision.

## Risks

The newer upstream host may lack generic child, output-limit, owner-question, or event-catalog capabilities on which Conductor relies; package installation alone is not compatibility evidence. Moving owner UI and required-event recognition can change replay and authorization, so tests must include invalid and unsupported records as well as successful runs. Requiring the bundle for Conductor-bearing sessions means a generic installation cannot show those sessions' chat until the bundle is explicitly enabled; it must give a clear refusal instead of a partial transcript. Client connection and account permissions remain for the separate adapter design. Two active notes are partially superseded only when the bundle ships: [source-launch assets](../../implemented/bug-fix/2026-11-01-conductor-source-launch-assets.md) retains installation-relative reads, preparation before boot, unchanged-byte no-ops, atomic publication, and fail-closed preparation, while package-owned preparation replaces CLI generation; [role-profile assets](../../implemented/feature/2026-10-24-conductor-role-profile-assets.md) retains the static WebP associations, relative resource metadata, and absence of runtime avatar rendering, while packed bundle resources replace the CLI copy. Both notes remain active and authoritative for those retained mechanisms.
