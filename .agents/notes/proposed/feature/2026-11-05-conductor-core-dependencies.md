# Agent Note: Conductor core dependency inventory

Status: proposed

English | [中文](2026-11-05-conductor-core-dependencies.zh.md)

## Problem

Biyocon Harness stays on its rc.7 foundation; the owner has dropped the upstream-sync track of [#68](https://github.com/Biyocon/biyocon-harness/issues/68). A later extraction should package Conductor as an independent DSH plugin for a newer DeepSeek Harness. Existing Conductor-driven changes outside `packages/conductor/*` and the separate `ui-conductor-subagent` package make that extraction non-trivial. The inventory below records the merged source dependencies at `c1a6877f9215b3fc973aaed5247d07d6e8f6dab5`, rather than promising compatibility with an unknown newer host.

## Proposal

Keep new Conductor code in `packages/conductor/*` and separate UI plugin packages. Avoid editing agent-loop, subagent, workflow, llm, system-prompt, tools, client-runtime and other shared packages. When a shared change is necessary, make it small and generally useful, record each changed source file, purpose and PR number in this inventory, and keep the dependency direction one-way: core never imports Conductor. A new core change must have an explicit general extension-point rationale and focused tests. The inventory is an extraction checklist, not a mandate to retrofit existing code or to sync upstream.

The historical `packages/extensions/tool-cordis/src/api-catalog.ts`, `packages/extensions/cordis-client-runner/src/client/slot-catalog.ts` and `packages/core/session/src/known-event-types.ts` changes are especially easy to confuse: the catalog files are generated projections, while the session file contains direct Conductor event-name registrations. #64's generic implementation is substantial, yet it is a dependency because Conductor's critic uses its identity and budget guarantees; its own Agent Note remains the authority on semantics. Existing owner UI in `ui-user-questions` is not a separate Conductor UI plugin; extraction should move its domain presentation, not copy the coupling into the new host.

## Alternatives considered

**Sync the fork first.** Rejected by the owner. A newer upstream would move the baseline while this dependency inventory is being established and could hide what is Conductor-specific.

**Treat every non-Conductor file in a PR as a core dependency.** Rejected because generated catalogs, snapshots, tests and broad localization are evidence or projections, not code that the extracted plugin must require. The source-file list still makes the runtime and host/UI couplings reviewable.

**Copy current core changes into a future host.** Rejected as a default: the target may already provide equivalent extension points. Compare capabilities and tests first, then retain only a small generic gap; never add a core-to-Conductor import.

## Acceptance criteria

The owner can locate each listed source file and merged PR, identify the generic versus Conductor-specific reason for the change, and see the planned `requiresTools` entry without treating it as shipped. A later Conductor PR updates this inventory whenever it changes a shared source file, with file, purpose and PR number; a future extraction checks the one-way import direction and maps each retained capability to the newer host.

## Risks

This is a first inventory from merged diffs, not proof that every changed line remains necessary on current master or a future host. Some files contain mixed generic and Conductor-specific behavior. The owner-card UI/RPC changes and direct session event registrations present the clearest extraction work. No upstream sync or phase-1 implementation follows from this note.
