# Agent Note: Devil's Advocate challenges analysis reports

Status: proposed

English | [中文](2026-10-28-conductor-analysis-critic.zh.md)

## Problem

Analysis currently accepts a producer's report after Auditor and Arbiter without an independent challenge to its reasoning. Auditor checks factual claims and file/line references; that does not establish that priorities, alternatives, risk trade-offs or recommendations follow from the cited material. The owner reports that CON-2026-0687 (CustomAgents) and CON-2026-7660 (biyocon-harness) both reached Arbiter acceptance without a Devil's Advocate critic. Reported role tokens were Detective 303K/378K, Strategist 150K/138K, Auditor 165K/196K and Arbiter 30K/26K, respectively. These are owner-reported observations, not replayed sessions; no private session content is included.

On [biyocon/master 45d316f](https://github.com/Biyocon/biyocon-harness/tree/45d316f852a7ad104375e07a148a48ca67f3b730), [admittedRoute and reportProducer](https://github.com/Biyocon/biyocon-harness/blob/45d316f852a7ad104375e07a148a48ca67f3b730/packages/conductor/conductor/src/intake.ts#L159-L179) still route Detective-entry recommendations through Detective → Strategist → Auditor → Arbiter, and an answer through its entry role → Auditor → Arbiter. Devil's Advocate can produce an entry-C report but does not challenge another report. [driveAnalysis](https://github.com/Biyocon/biyocon-harness/blob/45d316f852a7ad104375e07a148a48ca67f3b730/packages/conductor/conductor/src/analysis.ts#L153) drives those read-only stages. [recordGate](https://github.com/Biyocon/biyocon-harness/blob/45d316f852a7ad104375e07a148a48ca67f3b730/packages/conductor/conductor/src/state.ts#L235) requires an approved execution baseline only for implementation-C pass; [parseAnalysisState](https://github.com/Biyocon/biyocon-harness/blob/45d316f852a7ad104375e07a148a48ca67f3b730/packages/conductor/conductor/src/analysis-persistence.ts#L14) rejects analysis execution authority. The record format is [v4](https://github.com/Biyocon/biyocon-harness/blob/45d316f852a7ad104375e07a148a48ca67f3b730/packages/conductor/conductor/src/state.ts#L35).

## Proposal

Require a Devil's Advocate challenge on every analysis run, with no silent opt-out. Preserve the seven role identities and all required intake/preparation steps. For Detective-entry recommendations the report path becomes Detective → Strategist (producer) → Devil's Advocate (critic) → Auditor → Arbiter. For an answer it becomes entry role (producer) → Devil's Advocate (critic) → Auditor → Arbiter. An entry-C answer uses two fresh, distinct Devil's Advocate children: the first produces the candidate and the second challenges it. Typed dispatch mode (`producer` or `critic`), distinct child IDs, attempts, prompts, source sessions and stored outputs distinguish them; the critic receives the candidate and referenced material, not the producer's prior transcript. This is separation of work and context, not an assertion that the same role has an independent viewpoint. Arbiter must see that provenance and cannot accept a candidate reviewed only by its own producer child.

The critic precedes Auditor. It asks whether priorities, alternatives, omitted risks, assumptions and recommendations follow from the evidence; it does not recheck every file/line citation. Auditor then verifies facts and exact citations in the final candidate, including any factual premise promoted from the challenge. A reasoning failure returns to the producer and requires a new candidate, challenge and audit; a citation error alone stays with Auditor's existing repair path. Arbiter accepts only the latest exact candidate, valid challenge and fresh audit. This keeps critique and factual verification distinct and prevents auditing a candidate that critique will immediately replace.

### Challenge result and Gate C

Propose a dedicated `AnalysisChallenge` structured result: `run_id`, `purpose: analysis`, `candidate_hash`, `candidate_version`, ordered `material_ids`, `critic_child_id`, `critic_attempt`, `findings` with stable ID, severity (`minor`/`major`/`critical`), claim, rationale and material IDs, `conclusion: holds|does_not_hold`, and bounded summary. The runtime computes a challenge hash from validated content. The result has no execution baseline, implementation approval or command evidence. A Gate C history record binds mode `critic`, child/attempt, candidate hash, challenge hash and decision. The existing entry-C producer pass is explicitly mode `producer`; neither can impersonate the other. A `holds` result with unresolved major/critical findings is contradictory and rejected.

Validation rejects a foreign run, unknown material ID, stale candidate/version/hash, reused child or attempt, mismatched dispatch mode, duplicate/conflicting challenge, changed finding content under the same hash, out-of-order Gate C and an Arbiter decision without matching candidate/challenge/audit hashes. A malformed result is a report-validation failure at the critic, never a synthetic `holds`. Persist the exact candidate → challenge → audit → Arbiter links before dispatching successors; replay validates the same causal sequence and rejects a partially checkpointed or contradictory record. A crash before the challenge checkpoint cannot turn an unrecorded result into a pass; restart resumes only the durable stage or parks ambiguous dispatch for owner review.

This changes the durable run meaning: propose `CONDUCTOR_RECORD_FORMAT_VERSION = 5`. Every run has a required `analysisChallenges: CapturedChallenge[]` (empty for implementation); each entry stores the validated result, its runtime hash, candidate hash, critic child ID and attempt. Analysis Gate C history requires `mode: producer|critic` and the exact candidate hash; critic records also require the challenge hash and child/attempt. Analysis `ReportDecision` requires `challenge_hash` alongside its candidate/audit hashes. These v5 fields make producer and critic occurrences, replay order and Arbiter acceptance unambiguous. v4 has no challenge provenance and is rejected with the existing unsupported-format error, without migration or compatibility shim. Implementation-only v5 records keep their current authority rules. [#30 phase 2](https://github.com/Biyocon/biyocon-harness/issues/30) must take the next monotonic format version (v6 if it follows v5 directly), never reuse v5 with a different meaning.

### Rework, owner and authority

`does_not_hold` records a critic Gate C rework targeted at `reportProducer(admission)`; scope defects return to Detective, plan defects to Strategist, through the existing prerequisite rules. The producer emits a new version/hash, followed by a new critic child and Gate C assessment. The first two Gate C rework records consume `maxReworkPerGate: 2`; the third requested rework is recorded as Gate C escalation with the unresolved findings, not another producer dispatch. Gate A/B/E/G counters remain independent. Malformed critique consumes the same Gate C report-rework budget, unless it is a foreign/stale identity or authority violation, which fails closed and escalates immediately. Critical safety or authority findings escalate immediately with the exact reason; a substantive but repairable major finding uses rework. No verdict silently passes a challenge.

Reuse [#37's owner ledger and continuation](../../implemented/feature/2026-10-30-conductor-owner-escalation-resumption.md): exact run, candidate/challenge hash, gate history index, child attempt and required questions are stored in the existing question/answer/consumed/rejected ledger. `maxOwnerReassessmentsPerGate` remains independently bounded. Reuse required `conductor/owner-question-created`, `conductor/owner-response-recorded`, `conductor/owner-response-acknowledged`, `conductor/owner-continuation-consumed` and `conductor/owner-terminal-rejection` events and the existing owner card actions `approve`, `reject`, `answer_continue` (Godkend / Afvis / Svar og fortsæt). `approve` is offered only for a concrete validated proposal; an analysis answer or approved clarification may trigger one read-only reassessment, never execution approval. An owner reply cannot create an execution baseline, authorize implementation, reset Gate C rework, or reach Headsman, Ralph, Integrator or closeout. Implementing recommendations needs a separate implementation run and its own authorization.

### Input, cost and presentation

Give the critic the latest candidate report, its content hash/version, acceptance criteria, bounded material-reference index and selected excerpts from those references. Do not replay Detective's repository exploration or full child transcript. Permit `read` and `read_image` only on the admitted referenced material, plus `structured_output`; deny `grep`, `glob`, write, edit and shell to this critic dispatch. Validate paths/IDs at dispatch and tool use, and log exact selected excerpts and the model-visible challenge request as ordinary session messages/request headers, with the challenge result and Gate C state in `conductor/checkpoint`. A separate `conductor/child` event already carries role, attempt and gate; extend typed dispatch/stage data with producer/critic mode and exact child binding so [#56](https://github.com/Biyocon/biyocon-harness/issues/56) can show the role rather than the prompt/UUID. This proposal does not implement #56. A fresh child starts with no inherited gate badge. Web UI shows EN/DA text for role, attempt and `holds`/`does_not_hold` or pending/escalated, not color alone.

The owner's two reported runs used 648K and 738K tokens across the four listed roles. Estimate 20–40K additional tokens for one bounded critic attempt, about 3–6% of those totals; two reworks can mean three attempts (60–120K additional critic tokens), excluding producer reruns. Propose validated per-attempt input/output limits and a 120K critic-token run ceiling, counting provider-reported reasoning tokens; exhaustion parks an explicit owner escalation rather than skipping critique. Record usage per attempt and compare actual cost in keyless/provider tests before enabling the default. [#58](https://github.com/Biyocon/biyocon-harness/issues/58) owns Detective cost reduction; this design neither expands Detective input nor authorizes a second whole-repository exploration.

## Alternatives considered

**Critic after Auditor.** It repeats citation checking or invalidates an expensive audit when it demands a new candidate; challenge before audit is cheaper and keeps responsibilities distinct.

**Auditor as sole critic.** Auditor already owns factual and citation verification, so combining reasoning challenge with that pass hides which judgment failed and preserves the current gap.

**Optional or silent critique.** It allows an accepted analysis to bypass the owner's requested role and makes restart semantics dependent on an unrecorded choice. Mandatory critique has a visible token cost and a stable route.

**Treat a second Devil's Advocate child as fully independent at entry C.** A fresh session and separate mode prevent self-review of one child output, but the same role/model is not an independent discipline; provenance must state that limit.

## Risks

The added critic increases latency and tokens, especially after rework; the bounded input, usage ceiling and explicit owner stop prevent silent cost growth but do not reduce Detective's existing cost. Entry-C producer/critic children share a role/model, so the design guarantees separate sessions and evidence binding, not independent expertise. v4 runs cannot resume under v5; pre-release rejection is intentional. No runtime, schema or #30 phase-1 changes are part of this proposed note.
